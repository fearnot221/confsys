# ADR 0004 — Local roles and one-time operator bootstrap

Accepted 2026-10-15 for authorized Phase 1.2. The user's request authorizes implementation; the attachment provides acceptance detail, not evidence that any test passed. ADR 0003 remains the product boundary: each deployment serves one conference, with unrelated local identities and infrastructure.

Use two fixed roles with explicit typed permission grants in `apps/api/src/access/policy.ts`. Contracts enumerate supported keys but do not duplicate the mapping. No wildcard, numerical hierarchy, external policy engine, Redis role cache or new dependency. The authoritative matrix is in PERMISSIONS. Future resource/assignment/conflict policies must independently check their resource; admin has no implicit future grants.

Persist many-to-many bindings in `user_roles` and one immutable-in-normal-operation bootstrap marker in `access_control`. The operator CLI uses the selected instance's existing migrator credential; HTTP and worker never load/import this entry point or receive that credential. Runtime can lock the singleton but cannot update its marker columns. CLI also checks the connection role. Explicit apply requires exact configured public origin and a bounded reason. Default is preview. Same-target completed apply is a no-op, never a regrant; another target conflicts. No force/recovery backdoor, no first-public-user shortcut. Operator source records machine access, not verified human identity.

Serialize rare management writes on the singleton row, then revalidate the session under its user lock before policy/proof checks, then lock target. Existing auth locks only its own user before tokens/sessions. Target changes, credential epoch, revocation, audit and bootstrap marker commit together. Check at least one active, verified, password-bearing administrator after a change and before commit. Locks end with the transaction; no Redis lock or count-then-independent-update. Pool statement timeout is 3 seconds; unexpected failures roll back and return a safe failure, with no implicit retry of sensitive actions. Retry explicitly after rereading state. No lock on ordinary public reads/login beyond existing per-user auth locking.

Reuse `credential_version` for role/status/forced-logout fencing. Password verification occurs outside the user lock; login compares the version again under lock. Forced logout advances it even with no live session, to fence in-flight password checks. Repeated role grant/revoke and status transitions are no-ops without another epoch/revocation/audit success; each explicit forced logout is a new revocation command. Disable additionally revokes both token purposes. Restore keeps remaining bindings, does not regrant removed bindings, and cannot revive old proof/tokens/sessions. Self role/status changes are prohibited; self forced logout is allowed.

Recent password proof lives on the session and expires at five minutes (project policy, not a standards requirement). Successful password login sets it; restored pre-upgrade sessions have NULL and need real reauthentication. Reauthentication uses the existing password verifier, Redis limits, user lock and session validation; no client timestamp, no new password algorithm. MFA is still required before privileged production use.

Additive migration 0004 preserves 0001–0003, existing user/hash/verification/token/outbox/audit data and sessions. No backfill confers roles; no global logout. Do not run old and new API binaries together after access control is enabled: the old login creates sessions without the new proof field and old clients reject new DTO fields. Upgrade one selected instance with app processes stopped, migrate separately, start matching images. Recovery is reviewed roll-forward or coordinated same-instance backup restore, not an untested downgrade or clearing volumes.

Bounded offset pagination (max 50, offset max 100000) is chosen for this small administrative directory and audit viewer, with deterministic `(email,id)` / `(created_at,id)` ordering. Pages are not a transactional snapshot during concurrent insertions; users can refresh. Keyset pagination/search indexes are deferred until measured scale warrants them (ROADMAP). No general CRUD, export, bulk role updates, names/profile editing or invitation product.

Security direction checked against [OWASP Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html), [Authentication](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html), [Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html) and [PostgreSQL 17 locking](https://www.postgresql.org/docs/17/explicit-locking.html). These support server-side checks and transaction mechanisms; role names, five-minute policy and last-admin invariant are project decisions.
